# Frenet 分支阶段性进度汇报

日期：2026-05-28  
当前分支：`rollback/frenet-063ef43`

## 1. 工作目标

本阶段主要围绕 F1TENTH 静态随机障碍场景中的 Frenet 局部避障规划展开，目标是让车辆在全局中心线巡航的基础上，遇到赛道内随机静态障碍物时能够提前切换到 Frenet 轨迹束规划，生成可跟踪、可避障、可恢复中心线的局部路径，并通过 RViz、日志和 rosbag 支持复现实验与问题分析。

## 2. 已完成的主要工作

### 2.1 Frenet 局部规划器实现与接入

- 实现了基于参考线的 Frenet 坐标投影、采样和 `(s, d)` 到世界坐标的转换。
- 实现横向五次多项式与纵向四次多项式轨迹生成。
- 支持对 `d_final`、轨迹时长、终点速度进行枚举，生成 Frenet 候选轨迹束。（问题是计算效率目前不够高，可以参考一下把计算全都丢到GPU里面，使用CUDA并行计算的思路）
- 将 Frenet planner 作为 ROS 2 节点接入仿真系统：
  - 订阅全局路径、里程计、LaserScan 和地图；
  - 发布 `/local_trajectory` 给 LQR 控制器；
  - 发布 `/local_trajectory_speed_limit` 控制避障阶段速度；
  - 发布 `/frenet/debug/candidates` 供 RViz 可视化候选轨迹。

### 2.2 障碍物检测与安全约束

- 建立车体局部占据栅格，将 LaserScan 和静态地图障碍投影到局部 grid。
- 加入障碍物膨胀、轨迹走廊扫掠检测、前后 footprint 检查。
- 对候选轨迹增加硬约束过滤：
  - 不能与占据栅格碰撞；
  - 最小 clearance 必须大于 `min_clearance_m`；
  - 路径曲率不能超过车辆可跟踪上限；
  - 路径航向跳变不能过大；
  - 纵向进度必须保持前进。

### 2.3 轨迹选择与路径复用逻辑

- 为候选轨迹设计 cost 项，包括横向 jerk、纵向 jerk、时间、终点横向偏移、速度误差、clearance、曲率和平滑度。
- 加入 temporal/profile consistency，减少连续规划周期之间候选轨迹左右跳变。
- 加入 reuse 逻辑：
  - 如果当前周期无解，可短时间复用上一条安全轨迹；
  - 修复过“只缓存裁剪后路径”的问题，改为缓存完整候选轨迹，再根据车辆当前位置裁剪发布。
  - 后续已删除规划前 held path 提前返回逻辑，避免旧路径截胡当前周期新候选。

### 2.4 RViz 可视化与实验工具

- 增加 Frenet candidate RViz marker：
  - 浅蓝色线表示通过硬约束的 safe candidates；
  - 红色粗线表示最终选择并发布的路径。
- 增加随机障碍物鲁棒性测试脚本：
  - 支持多 seed 批量测试；
  - 支持指定圈数、目标速度、避障速度、障碍数量和障碍尺寸；
  - 支持是否录制 rosbag；
  - 输出 summary CSV/JSON 和 launch/tracking 日志。
- 增加 RViz 启动路径，用于人工观察局部候选、最终轨迹和车辆实际跟踪情况。

### 2.5 参数调优与高速场景支持

- 针对 `target_speed=3.0 m/s`、`avoidance_speed=1.5 m/s` 做了高速度参数预设：
  - 扩大局部 grid 前向范围；
  - 增加 Frenet 激活距离；
  - 调整发布路径长度；
  - 调整路径保持和重规划阈值；
  - 调整横向采样、速度采样和轨迹时域。
- 将固定地图测试和随机障碍测试中的 Frenet 参数统一到 `preset.py`，避免 shell 脚本、launch 和测试 runner 参数漂移。

### 2.6 测试与回归验证

- 增加 Frenet 单元测试，覆盖：
  - 多项式边界条件；
  - Frenet 投影与采样；
  - 占据栅格碰撞检测；
  - 候选轨迹 cost；
  - temporal consistency；
  - 随机障碍测试 runner 的日志统计。
- 当前容器内单元测试结果：`45 passed`。
- 做过 10 组随机障碍 rosbag 批量测试：
  - 一轮结果为 `8/10 passed`；
  - seed000、seed005 出现碰撞；
  - rosbag 和 tracking log 用于后续定位问题。

## 3. 遇到的主要问题

### 3.1 候选轨迹存在，但最终路径仍贴近障碍

RViz 中出现过“左右两边有浅蓝色安全候选，但红色最终路径仍接近中心线/障碍物”的现象。分析后发现原因不止一个：

- 浅蓝线是 debug candidate marker，可能来自上一帧保留结果，不一定表示当前周期最终参与选择的候选。
- 红线曾可能来自 held path，而不是当前重新规划出的 raw best。
- held path 在规划前执行，如果旧路径 clearance 仍高于阈值，就会直接复用并提前返回。
- 该逻辑已被删除：现在进入 Frenet active 后默认先重新规划，只有当前周期无 safe candidate 时才尝试 reuse。

seed000 曾在提高 hold 阈值后快速回归通过；当前最新逻辑进一步删除 hold，后续还需要重新跑 seed000/seed005 和 10 seed 批量验证。

### 3.2 安全裕度与可通行性之间矛盾

早期调参中发现：

- 安全裕度过大时，候选轨迹容易全部被过滤，出现 `No safe Frenet candidate`。
- 安全裕度过小时，规划器认为路径安全，但 LQR 实际跟踪存在横向误差和航向误差，车体前部可能扫到障碍物。
- 单纯增大膨胀半径会减少碰撞，但会显著增加无解概率。

当前采用的方向是：

- 保持几何膨胀不过度保守；
- 用 footprint/corridor 覆盖车体扫掠；
- 把低 clearance 惩罚统一合并进 `score_candidate()`，不再单独使用 clearance preference 后处理；
- 删除 held path 和 temporal 二次选择，减少状态机分支。

### 3.3 计算耗时与采样密度矛盾

提高 `d` 采样密度、增加短时域和低速终点后，候选数量明显增加，CPU 计算耗时变高。曾评估过 CUDA 轨迹生成，但当前容器没有可用 CUDA 设备，因此没有真正跑 GPU 加速。后续可优先考虑：

- CPU NumPy 向量化轨迹批量生成；
- 并行化候选碰撞检查；
- 进一步评估 CUDA/CuPy 或自定义 CUDA kernel。

### 3.4 规划与控制耦合不足

部分碰撞不是 base_link 中心直接撞障碍，而是车辆前部在较大航向误差、转向饱和或跟踪误差下扫到障碍。这说明只用几何轨迹中心线 clearance 判断还不够，需要考虑控制器实际跟踪能力。

后续可以引入：

- 基于当前 `e_y`、`e_psi` 的动态安全裕度；
- 对高曲率、高 heading jump、高跟踪误差风险轨迹增加惩罚；
- 在接近障碍时进一步降低局部限速。

## 4. 当前状态

当前 Frenet 分支已经具备完整的静态障碍避障链路：

- 能生成 Frenet 候选轨迹；
- 能做局部占据栅格碰撞检测；
- 能发布候选可视化和最终局部路径；
- 能通过随机障碍批量测试脚本进行回归；
- 能录制 rosbag 支持复盘。

但它还不是完全稳定版本。当前已知重点风险是：

- 个别随机 seed 下仍可能出现碰撞或短暂无解；
- candidate cost 和 LQR 跟踪之间仍需要更严格的一致性约束；
- 高采样密度下计算耗时仍偏高。

## 5. 下一步建议

1. 继续用 seed000、seed005 和 10 seed 批量测试验证“无 hold、无二次筛选、clearance cost 内化”后的稳定性。
2. 增加“最终发布路径 clearance”和“candidate clearance/cost/d_final”的结构化日志，减少只靠 RViz 判断的歧义。
3. 将安全裕度做成控制器感知：根据当前横向误差、航向误差和速度动态增加 clearance 要求。
4. 优化候选生成和碰撞检测性能，优先做 NumPy 向量化，再评估 CUDA 并行。
5. 在实验日志中持续记录每次参数改动、失败 seed、失败原因和验证结果，避免调参过程不可追溯。
